排查手册

按症状检索的排障手册。示例一律用占位符，不写真实地址。

目标

部署与使用过程中出现异常时，按本页顺序定位：先用「命令手册」取事实，再到「常见错误与排查」里对照症状。每一项都给出可执行的判定动作，读完应当能判断是自己配置的问题、线路的问题，还是环境的问题。

三个入口先记住：服务端自检 bin/deploy/check/server.sh、客户端验收 bin/deploy/client/verify.sh、加固验收 bin/harden/audit.sh。三者的输出含义都在本页说明。

命令手册

确认某条连接走了哪个出站

sing-box 的 Clash API 给每条连接一个 chains 字段，["direct"] 是直连，["proxy"] 是走节点。

# 从客户端配置里读控制端口与密钥，再查连接列表
S=$(grep -o '"secret":"[^"]*"' config.json | cut -d'"' -f4)
C=$(grep -o '"external_controller":"[^"]*"' config.json | cut -d'"' -f4)
curl -s -H "Authorization: Bearer $S" "http://$C/connections" | grep -o '"chains":\[[^]]*\]' | sort | uniq -c

既有 direct 又有 proxy 才算分流正常；全是 proxy 说明国内直连规则没生效。

常见错误与排查

国内站点全部打不开，境外却正常

两种已知原因，看日志区分。

其一，route.auto_detect_interface 取值和平台有关。

场景取值原因
Android / iOS（TUN + auto_route）true（默认）直连出站必须绑到物理网卡，否则国内流量会绕回 TUN，表现为「国内无法直连」
Windows / macOS 桌面先 true；报错再改 false多网卡 / 驱动环境下接口绑定可能返回 10049，日志里是 not valid in its context
只用 mixed / 系统代理（无 TUN）无所谓没有路由改写，不需要绑定

桌面要覆盖成 false，在服务器重渲染这台设备时给变量，再重新导出：AUTO_DETECT_INTERFACE=false DEFAULT_INTERFACE=网卡名 sudo -E bash bin/deploy/device.sh export laptop。只关探测不绑网卡会让直连打环，两个变量必须一起给。实测同一份配置只改这一个值：true 时请求失败、DNS lookup failed；false 时 DNS NOERROR、HTTP 200。

其二，同时开了两个代理客户端。比如 Clash Verge 与本方案的 sing-box 同时运行，两边抢 DNS、抢系统代理、抢路由，还会看到 DNS 被改写成假地址 198.18.x.x 之类。处理办法是同一时间只留一个，退出另一个后重启留下的那个。

启动报 detour to an empty direct outbound makes no sense

sing-box 1.12+ 不允许 DNS 服务器的 detour 指向一个「空」direct 出站，也就是 {"type":"direct","tag":"direct"} 这种不带任何选项的直连：

FATAL start service: start dns-transport: start dns/https[dns-cn]:
      detour to an empty direct outbound makes no sense

两种改法，语义不同：

  • 删掉该 DNS 服务器的 "detour": "direct" → 跟随默认出站，解析要等隧道建好
  • 给 direct 出站加任一选项让它不再是空出站，例如 "domain_resolver": { "server": "dns-cn" } → 国内域名仍走直连解析

本方案用第二种。bin/deploy/client/render.sh 生成的配置已经带上。

sing-box check 查不出这个错。check 不初始化 DNS 传输，所以「能过 check」不代表能启动，必须以真正启动一次为准。

启动报 missing tags、missing server field、dependency not found

三类报错都出自同一原因：出站或 DNS 结构不完整。手写或拼装配置时最容易踩到。

报错原因动作
initialize outbound[N]: missing tags某个 urltest / selector 分组的 outbounds 是空数组给分组补上真实节点标签；只有一个节点时直接删掉分组，让路由指向该节点
parse dns rule[N]: missing server fieldDNS 规则缺 server。1.12 起 action: route 的 DNS 规则必须带服务器每条 DNS 规则补 "server": "dns-cn" 这类字段，或删掉该条规则
start outbound: dependency[X] not found for outbound[Y]分组里写的成员 tag 在 outbounds 中不存在对齐标签，或把成员出站补进 outbounds
duplicate outbound/endpoint tag: direct配置里出现两个同名出站，常见于把完整的 direct / block 又写了一遍只保留一份；模板已内置这两个出站
路由规则加了却不起作用规则带了 action: route 却没写 outbound这种规则不报错，命中后沿用最终出站。服务器直连规则漏了出站，表现就是 SSH 被绕进隧道

企业管控机器：启动即 10049

症状是启动立刻退出，日志里是 dial tcp 某DNS:443: connectex: The requested address is not valid in its context.，而 sing-box check 通过。境内外站点同时不可用，因为节点域名的解析在启动阶段就失败。

先确认是不是这一类：客户端看到的系统 DNS 是内网地址，网卡上挂着第三方过滤驱动。Windows 上可以这样看：

Get-DnsClientServerAddress -AddressFamily IPv4 | Where-Object { $_.ServerAddresses }
Get-NetAdapterBinding | Where-Object { $_.Enabled -and $_.ComponentID -notlike "ms_*" }

判据是目标端口：绑定网卡时连公共 DNS 的 443 与 853 立即被拒，53 正常，连节点 IP 的 443 也正常。这种情况来自企业终端策略，禁止用 DoH/DoT 绕过内网 DNS，改服务端参数没有用。

方案一，给直连出站指定源地址。在客户端配置里只给 direct 出站加一项，值填本机在当前网络的 IPv4 地址：

{ "type": "direct", "tag": "direct", "domain_resolver": { "server": "dns-cn" },
  "inet4_bind_address": "192.168.8.150" }

触发拦截的是按接口绑定 socket，指定源地址走的是另一条路径，实测放行。填之前先用 ipconfig 确认，换网络后这个值要跟着改。

方案二，国内解析交给系统。把国内 DNS 换成系统解析，由操作系统去问内网 DNS：

{ "type": "local", "tag": "dns-cn" }

不再有直连公共 DNS 的 443 出站。系统若启用了 DNS over HTTPS，加密由操作系统承担。

方案三，绑到虚拟网卡。策略绑定在物理网卡上，把出站绑到一块 NAT 出去的虚拟网卡可以避开命中。需要管理员与 Hyper-V，本机未做验证，仅作为前两条都不可行时的备选：

New-VMSwitch -Name singbox -SwitchType Internal
New-NetIPAddress -IPAddress 192.168.199.1 -PrefixLength 24 -InterfaceAlias "vEthernet (singbox)"
New-NetNat -Name singbox-nat -InternalIPInterfaceAddressPrefix 192.168.199.0/24
# 之后渲染设备配置时指定该网卡
AUTO_DETECT_INTERFACE=false DEFAULT_INTERFACE="vEthernet (singbox)" sudo bash bin/deploy/device.sh export 设备名

验收判据与方案一相同：启动不再出现 10049，国内站点仍直连。

不要用「关掉接口绑定还开着 TUN」来绕。auto_detect_interface 关掉又没给 default_interface 时，直连流量会从隧道出口绕回自己，表现为国内站点变慢或走境外。

日志里的 REALITY: processed invalid connection

不是故障。REALITY 对任何拿不到正确凭据的 TLS 连接都会记这一行，并把它转发给伪装站点。扫描器、浏览器直接访问服务器 IP、参数写错的客户端，都会产生它。

判断看来源：不是自己的宽带地址就忽略；是自己的地址且客户端连不上，说明参数不匹配，对比这六项：服务器地址、端口、SNI、UUID、REALITY 公钥、short_id，外加 flow 必须一致。

解析失败：lookup 某域名: (exchange6: EOF | exchange4: EOF)

exchange6 与 exchange4 是 sing-box 对同一个域名分别走 IPv6 与 IPv4 的两次 DNS 查询，EOF 表示 DNS 连接被关闭。常见原因有两个：查询走的是经代理的 dns-remote，而那一刻隧道还没建好或握手失败；或者代理刚重连，旧连接被关掉。

当前配置下国内域名走直连 DNS，不依赖隧道，只有海外域名才需要隧道。海外域名偶尔 EOF 时，先确认隧道已就绪再重试。

启动告警

  • implicit default HTTP client using default outbound for remote rule-sets is deprecated：1.14 起不再隐式用默认出站下载规则集，1.16 会移除。当前模板已修，配置里显式写了顶层 http_clients 与 route.default_http_client，重新渲染一次客户端配置即可。仍看到这条说明 JSON 是旧版模板生成的。
  • REALITY: processed invalid connection：含义与处理见同名小节。

移动端闪退：NoSuchElementException

java.util.NoSuchElementException
  at java.util.LinkedList.removeFirst(LinkedList.java:282)
  at io.nekohasekai.sfa.compose.screen.log.LogViewModel.togglePause(...)

崩在日志页面点「暂停」的时候，且日志列表为空。这是 sing-box Android 客户端（SFA）的界面缺陷，与应用配置无关。规避办法是不要在日志为空时点暂停，或升级 App。

刚重启就看结论，三个坑

重启之后立刻自检，读到的往往还不是新进程的状态。下列结果在 Debian 13 上实测。

重启竞态。连续三轮都是「active 但 443 未监听」，从 restart 返回到端口可用约 240 ms，要下载规则集或加载证书时更长。

systemctl restart sing-box
systemctl is-active sing-box     # active：服务已拉起
ss -tln | grep ':443 '           # 可能还是空：监听尚未建立
日志要按启动时间切。直接 journalctl -u sing-box -n 300 会把上一轮失败留下的 FATAL 一起读出来，看起来像当前版本起不来。按本次启动看：
journalctl -u sing-box --since "$(systemctl show -p ActiveEnterTimestamp --value sing-box)"
服务端自检脚本已经这么做。

端口就绪要等监听，不要等进程。判定端口都用轮询，比 sleep 3 稳：慢机器上够用，快机器上不浪费。UDP 用 ss -uln。

for i in $(seq 1 100); do
  ss -tln | grep -q ':443 ' && { echo 就绪; break; }
  sleep 0.1
done

CAP_DAC_OVERRIDE：root 不绕过文件权限。能力集里去掉它之后，uid 0 只是一个普通用户：目录属主是 sing-box、权限 750 时，root 落在「其他人」，没有 x 就进不去。复现：

install -d -m 750 -o sing-box -g sing-box /tmp/dac2
echo hi > /tmp/dac2/f && chown sing-box:sing-box /tmp/dac2/f && chmod 640 /tmp/dac2/f
cat /tmp/dac2/f                                   # hi
capsh --drop=all -- -c 'cat /tmp/dac2/f'          # Permission denied

这是降权后「配置读不到」的根因之一。处理见第 3 页的沙箱一节：目录属主跟随单元 User，或用 bin/deploy/check/selfcheck.sh --fix-dac 修正。

本机 TUN 捕获 SSH

自己电脑上跑着 TUN 客户端时，连服务器的 SSH 也会被隧道接管，服务器 IP 不在隧道的直连规则里，握手就死在半路。症状是 kex_exchange_identification: Connection closed、Connection closed by UNKNOWN port 65535，或者干脆超时，但服务器明明在跑。

nc -vz 报「能通」不能当证据。TUN 在本地就把 TCP 握手接住了，连本来没服务监听的端口也会「成功」。判断：route -n get <服务器IP> | grep interface，看到 utunX 就是被接管了。

正确的修法在代理配置里：把服务器自己的 IP 设为直连。规则要加在真正持有 utun 的那个客户端上，先 pgrep -fl 'clash|mihomo|sing-box' 看一眼。本手册的 bin/deploy/client/render.sh 会自动给 sing-box 写这条规则，旧配置重新渲染一次就修好。

# sing-box：route.rules 的第一条
{ "ip_cidr": ["<服务器IP>/32"], "action": "route", "outbound": "direct" }

# Clash / Mihomo / Clash Verge（用「全局扩展配置 → 规则」的 prepend，别改订阅本体）
- IP-CIDR,<服务器IP>/32,DIRECT,no-resolve

临时手段是不改代理配置，加一条宿主路由绕开隧道，或部署期间先关掉 TUN。用完删掉：

# macOS
sudo route -n add -host <服务器IP> <你的局域网网关>
# Linux
sudo ip route add <服务器IP> via <局域网网关>
# 撤销
sudo route -n delete -host <服务器IP>

测量视角

本机有 TUN 时，测出来的每一个数字都可能是假的。跑着代理客户端的机器会把自己的 curl / nc 也送进隧道，「延迟很低」「端口通」都是隧道内的回环表现，不是真实链路。验收前先确认测试机器上没有任何代理客户端在跑。

唯一在隧道开启时仍然可靠的信号是 ping，ICMP 通常不被代理接管，能给出到源站的真实往返延迟。常用组合：

ping <服务器IP>                      # 真实 RTT（绕过 TUN）
mtr -r -c 200 <服务器IP>             # 真实丢包与抖动
curl -o /dev/null -s -w '%{time_starttransfer}\n' https://www.google.com   # 走代理后的 TTFB

「连得上但只有几 KB/s」这类限速要区分两种情况：scp 传 10MB 文件很快、走代理下载极慢，是协议被限速，换 IP 没用，得换传输协议；nc 直接超时、而境外节点一切正常，是 IP 被封，换 IP 才有用。
