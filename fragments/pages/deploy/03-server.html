3 · 服务端配置与自检

把第 2 页生成的参数渲染成 sing-box 配置、启动服务，用自检脚本确认监听、日志与证书都对；随后降低进程权限，并建立按设备发放的凭据体系。读者是维护这台节点的人。

目标

本页做完应达到：服务以非 root 身份在 systemd 沙箱内运行、REALITY 入口在监听、自检十项全绿、设备名单可增删并能为每台设备生成独立配置。

准备工作

  • 第 2 页已跑完，/etc/sing-box/deploy.env 与 devices.list 存在
  • 当前 SSH 会话保持打开，另开一个终端备用
  • 启用 Hysteria2 时，先完成第 4 页的证书，否则渲染会因缺证书失败

实施步骤

渲染配置并启动

cd /root
bash bin/deploy/one/server.sh
bash bin/deploy/check/server.sh

bin/deploy/one/server.sh 用 deploy.env 渲染配置，交给 sing-box check 校验，通过后才重启服务；校验不通过不会覆盖旧配置。bin/deploy/check/server.sh 输出十项检查，全绿再往下走，各项含义见排查手册。

加固：降权与 systemd 沙箱

默认的单元文件让 sing-box 以 root 全权限运行。它是唯一监听公网、解析密文的进程，值得收一次权限。脚本幂等，随时可以复查或退回。一键脚本把这一步固定排在 hy2 之后、porthop 之前。

sudo bash bin/deploy/one/harden.sh           # 建 system 用户、收权限、重写单元、重启并自检
sudo bash bin/deploy/one/harden.sh --minimal # 只降权，不加沙箱指令
sudo bash bin/deploy/one/harden.sh --check   # 只看现状
sudo bash bin/deploy/one/harden.sh --uninstall  # 用备份的 .orig 覆盖回去并重启
做了什么为什么
User=sing-box 与 CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_BIND_SERVICE CAP_NET_RAW只需要三项能力：操作 nftables 与路由、绑 443、创建 TUN，其余 root 权限一律不给
/etc/sing-box 归 root:sing-box，目录 750、文件 640配置里有 REALITY 私钥与证书私钥，只有该组可读
ProtectSystem=strict、ProtectHome、PrivateTmp、ReadWritePaths=/var/lib/sing-box文件系统只读，唯一可写是自己的运行目录
ProtectKernelTunables、ProtectKernelModules、ProtectKernelLogs、ProtectControlGroups、ProtectClock、ProtectHostname、ProtectProc=invisible内核面全部收掉，nftables 走 netlink 不受影响
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_NETLINK、RestrictNamespaces、MemoryDenyWriteExecute、SystemCallFilter=@system-service只留网络相关的地址族与系统调用

设备凭据管理

bin/deploy/device.sh 在服务器上就地完成：改名单，重渲染服务端，重新生成那台设备的客户端 JSON。它不自己实现任何 sing-box 逻辑，渲染一律走现有脚本，不会与模板漂移。

sudo bash bin/deploy/device.sh list
sudo bash bin/deploy/device.sh add laptop [desktop|android|ios]   # 默认 desktop
sudo bash bin/deploy/device.sh rotate laptop                       # 换凭据，旧配置立刻失效
sudo bash bin/deploy/device.sh revoke laptop                       # 删掉，两条入口同时失效
sudo bash bin/deploy/device.sh render laptop                       # 只重渲染客户端配置
sudo bash bin/deploy/device.sh export laptop                       # 渲染并打包，附校验和与 URI.txt
sudo bash bin/deploy/share.sh laptop                               # 只打印这一台的分享链接

产品在 /etc/sing-box/clients/sing-box-client-<名字>-<平台>.json，export 的压缩包在 /etc/sing-box/clients/dist/。传输由客户端发起，源在服务器一侧，端口用 -P：

# 在客户端执行
scp -P 你的SSH端口 root@服务器IP:/etc/sing-box/clients/dist/laptop-*.tar.gz* /tmp/

不想每次写端口与 IP 时，在客户端的 ~/.ssh/config 里配别名：

Host vps
  HostName 服务器IP
  User root
  Port 你的SSH端口
# 之后可以写成
scp vps:/etc/sing-box/clients/dist/laptop-*.tar.gz* /tmp/

一台机器要出多份时，凭据按名字算，建两条各管一个平台，各自能单独吊销：

sudo bash bin/deploy/device.sh add laptop desktop
sudo bash bin/deploy/device.sh add laptop-android android
每台设备只发它自己那一份。整个 devices.list 落到任何一台机器上，等于把所有设备的凭据都给了它。名单本身要进 .gitignore 或单独加密存放。
add、rotate、revoke 都会重启 sing-box。当前活跃会话不会断，但新连接会短暂受影响。

检查与验证

bash bin/deploy/check/server.sh        # 十项全绿
sudo bash bin/deploy/one/harden.sh --check
ls -l /etc/sing-box/clients/           # 设备产物按 名字-平台 命名

加固的判定不是「服务 active」就算过。sing-box 起来后还要几十到几百毫秒才绑定端口，只看单元状态会把「还在绑定」误判成失败，因此脚本会等端口：服务 active 且 VLESS_PORT 在监听，启用 Hy2 时再要求 HY2_PORT/udp 在监听，最多等 20 秒，任一条件不满足就回滚。

--check 的关键三行：生效 User 应为 sing-box，StateDirectory 应为 sing-box，沙箱应为「完整」。另有两行用于排除干扰：FragmentPath 与 DropInPaths，后者不为空说明有 drop-in 覆盖了单元。

重渲染会把配置权限改回 600 root:root。降权后 sing-box 读不到，表现为 read config at …: permission denied。渲染脚本已改用 install_service_file，按单元里的 User= 自动落成 640 root:<该用户的组>；手工 install -m 600 覆盖过配置的，补 chgrp 后重启即可。

回退与卸载

场景动作
撤销沙箱，回到 root 全权限sudo bash bin/deploy/one/harden.sh --uninstall，用 .orig 覆盖单元并重启
单台设备退役sudo bash bin/deploy/device.sh revoke 名字，随后删除对方机器上的 JSON
凭据泄露sudo bash bin/deploy/device.sh rotate 名字 并重新导出分发
整体清除bash bin/deploy/deploy.sh --uninstall --purge --yes

原单元备份在 /etc/systemd/system/sing-box.service.orig，只在首次加固时写一次，重复执行不覆盖。用 bin/deploy/one/install-singbox.sh 重装 sing-box 会把单元覆盖回未加固版本，重装后需要再跑一次加固。

命令手册

# 只生成配置，不改系统、不重启
bash bin/deploy/one/server.sh --dry-run

# 服务状态与日志（只看本次启动之后）
systemctl status sing-box
journalctl -u sing-box --since "$(systemctl show -p ActiveEnterTimestamp --value sing-box)" --no-pager
journalctl -u sing-box -n 50 --no-pager

# 重启与沙箱自查
systemctl restart sing-box
sudo bash bin/deploy/check/selfcheck.sh            # 逐组属性试验，指出哪一组挡住启动
sudo bash bin/deploy/check/selfcheck.sh --fix-dac  # 按生效用户修正目录属主
sudo bash bin/deploy/check/selfcheck.sh --recover  # 退回原单元
只看日志用 --no-pager。在极简终端里直接跑 journalctl 会进分页器并提示 WARNING: terminal is not fully functional，那不是服务报错。

参数说明

devices.list 一台设备一行，三列依次为名字、凭据、平台：

# 名字 凭据 平台
main   af2358a4-df32-419c-9774-63a44c540970  desktop
phone  9b2c1d70-3e44-4a1b-8c02-7e5d9f10a333  android

一个凭据同时充当 VLESS 的 uuid 与 Hysteria2 的 password，所以删一行就是吊销那台设备，两条入口同时失效。服务端的 users 数组就是从这份名单渲染的，改名单后重跑 bin/deploy/one/server.sh 即生效。改凭据请用 device.sh，不要手改名单。

项取值说明
--minimal开关加固时只降权，不加沙箱指令
--check开关只报告现状，不改动文件
--uninstall开关用 .orig 覆盖单元并重启
device.sh add名字 [平台]平台取值 desktop / android / ios，默认 desktop
device.sh export名字渲染并打包，包内附 SHA256SUMS

常见错误与排查

沙箱下起不来时，脚本会自动回滚到 .orig，原服务照旧运行。原因看 journal 里的 status=：

status=含义先删哪一组
226/NAMESPACE某项命名空间或文件系统隔离加不上先去掉 ProtectSystem=strict、ProtectHome、PrivateTmp，逐条加回
203/EXEC执行阶段被拒：二进制路径、权限或能力不够先跑 --minimal，确认与 User= 及能力集无关
降权后 chdir … permission denied/var/lib/sing-box 仍是 root:root 700ls -ld /var/lib/sing-box 应显示 sing-box sing-box；脚本已显式 chown 并用 StateDirectory 兜底
回滚后仍 chdir … permission denied原单元以 root 运行，但能力集里没有 CAP_DAC_OVERRIDE，root 落在「其他人」，750 的 o 位没有 xchown -R root:root /var/lib/sing-box && chmod 700 /var/lib/sing-box
重装后 chdir … permission denied单元运行用户与目录属主不一致bash deploy.sh --only install --overwrite --yes 会按单元实际用户归位
initialize cache-file: … permission deniedcache.db 是上一次以其他用户运行留下的重跑 bash deploy.sh --only server --overwrite --yes，重启前会递归归位
1 且日志有 permission denied配置、证书或运行目录读不到ls -l /etc/sing-box 应为 root:sing-box、目录 750、文件 640
1 且日志有 operation not permitted系统调用被 SystemCallFilter 拦下去掉 SystemCallFilter 与 SystemCallErrorNumber

二分顺序：先 --minimal 确认降权本身没问题，再加回文件系统组，最后加进程组。加回时一次只放一组，每轮都看 systemctl is-active 与 ss -tlnp。

改完会重启 sing-box。重启后脚本验证「服务 active + 端口在监听」，任一不满足就回滚到原单元。沙箱内起不来时，多半是某个 Protect* 或 SystemCallFilter 挡了 TUN 与 netlink，删掉对应一行再跑。
