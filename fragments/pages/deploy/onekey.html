一键脚本

deploy.sh 把 7 个步骤串起来：先扫描每一步是否已配置，再让你决定「复用 / 覆盖 / 跳过」。它由 build-onekey.sh 自动生成，内容就是 lib.sh + steps/*.sh + 驱动逻辑。

快速开始

scp -r bin root@你的服务器IP:/root/
ssh root@你的服务器IP
cd /root/bin/deploy && bash deploy.sh

不带参数就是交互模式。想先看看它会做什么：bash deploy.sh --dry-run。

已配置的步骤默认「复用」，只有你选 o 才会重跑并覆盖。

参数

参数作用
--reuse已配置的步骤一律复用，不提问
--overwrite已配置的步骤一律重跑并覆盖
--only a,b只跑指定步骤（system,install,secrets,hy2,server,harden,porthop）
--skip a,b跳过指定步骤
--yes不再确认（配合 --reuse 可全自动）
--dry-run只打印计划和将执行的步骤
--status只看每一步的状态
--uninstall卸载，保留 deploy.env 与证书
--purge卸载并删除 deploy.env / 证书
--reinstall卸载并重装（等价于 --purge 后全量覆盖）
--rotate-secrets重建密钥时换掉所有客户端可见的密钥：REALITY 密钥对、short_id、HY2 混淆密码。已导出的客户端配置立即失效（默认沿用，交互模式会再问一句）

步骤与依赖

deploy.sh 的 7 个步骤名与 部署手册的编号不是一一对应（它把「装 sing-box」和「生成密钥」拆成两步，把 Hysteria2 拆成发证与端口跳跃两步，并在服务端配置之后固定跑一次加固），对照如下：

手册对应 deploy.sh 步骤在哪台机器
1 系统初始化system服务器
2 装 sing-box + 生成密钥install → secrets服务器
3 服务端配置 + 自检server → harden服务器
4 Hysteria2（可选）hy2（证书，排在 server 之前）→ porthop服务器
5 客户端配置不在本脚本内客户端机器
6 验收 + 备份不在本脚本内两边
步骤文件可选已配置的判定
systemsteps/10-system.sh否sysctl 存在 + ufw 已启用 + BBR 已开 + 密码登录已关
installsteps/20-install.sh否二进制与 systemd 单元都在
secretssteps/30-secrets.sh否deploy.env / client.env / devices.list 都存在
hy2steps/35-hy2.sh是证书存在且 ENABLE_HY2=1
serversteps/40-server.sh否config.json 存在且服务在运行
hardensteps/55-harden.sh否单元含 User=sing-box 与 NoNewPrivileges=yes，服务运行中
porthopsteps/60-porthop.sh是iptables 里已有重定向规则

表里的顺序就是执行顺序。两个可选步骤只在 ENABLE_HY2=1 时执行；否则自动跳过并说明原因。hy2 排在 server 之前：渲染服务端配置时要读 cert.pem / key.pem，缺证书时 server 直接失败。harden 排在 server 之后、porthop 之前：沙箱化后要验证 Hy2 端口，证书与服务端配置都已就位时 8443 才会监听。
ENABLE_HY2 是在 secrets 步骤里写进 deploy.env 的，所以「是否跑 hy2」按执行到该步时的取值判断：在 secrets 的提问里回答启用，同一轮就会接着签发证书，不必再用环境变量预先声明。
system 那一行的「密码登录已关」在没有可用公钥时不计入未配置：第 1 页会提示你先 ssh-copy-id，而不是反复报错。

卸载会删什么

  • 停用并删除 sing-box 服务、二进制、systemd 单元、/var/lib/sing-box
  • 删除 config.json、证书、Hysteria2 的 iptables 规则
  • 删除本项目加的 ufw 规则（443、8443-8447）与 sysctl.d 优化文件
  • --purge 额外删除 deploy.env / client.env
不会动的东西：SSH 端口的 ufw 规则、ufw 的启用状态、swap、/root/backups 里的备份。卸载后仍保持 SSH 可登录。

改步骤后重新生成

# 改 steps/*.sh 或 onekey/driver.sh 之后
bash fragments/build/build-onekey.sh
# 生成 deploy.sh（会自动做 bash -n 语法检查）

deploy.sh 是生成物，不要手改；单步入口（bin/deploy/one/system.sh 等）也调用同一份 steps/*.sh，所以两条路径的行为永远一致。

常见用法

# 只重做服务端配置（改完 REALITY_DEST 之类）
bash deploy.sh --only server --overwrite --yes

# 有域名后补开 Hysteria2
DOMAIN=vps.example.com CF_TOKEN=xxx ACME_EMAIL=me@example.com \
  bash deploy.sh --only hy2,server --overwrite --yes

# 完全重装（连密钥一起换）
bash deploy.sh --reinstall --yes

# 怀疑环境被污染，先卸载干净再来
bash deploy.sh --purge --yes && bash deploy.sh --yes

跑完之后

所有步骤成功时脚本最后会打印下面这几条，命令里的脚本路径已换成本机实际位置。它们做的是同一件事：把凭据按设备发给客户端。

下一步
  当前设备：mac
  新增设备：sudo bash /root/bin/deploy/device.sh add <名字> [desktop|android|ios]
  导出这一台的配置：sudo bash /root/bin/deploy/device.sh export <名字>
  换凭据：sudo bash /root/bin/deploy/device.sh rotate <名字>　　吊销：sudo bash /root/bin/deploy/device.sh revoke <名字>
  客户端导入后验收：bash bin/deploy/client/verify.sh

export 会把这一台的 JSON 打包成 /etc/sing-box/clients/dist/<名字>-<UTC时间>.tar.gz，并打出填好 SSH 端口、用户与服务器 IP 的 scp 命令。传输由客户端发起，源在服务器一侧、目标在本地当前目录：

[+] 已导出：/etc/sing-box/clients/dist/mac-20261026T123626Z.tar.gz（4.0K）
[+] 包内校验和：ed1509c7a459c75486e38c7fd1902a443947e57b7465fcde4d9851864876c671
[+] 分发（在客户端执行；源在服务器，目标在本地当前目录）：
[+]     scp -P 4061 root@203.0.113.9:/etc/sing-box/clients/dist/mac-20261026T123626Z.tar.gz root@203.0.113.9:/etc/sing-box/clients/dist/mac-20261026T123626Z.tar.gz.sha256 .
[+] 校验并解包：sha256sum -c mac-20261026T123626Z.tar.gz.sha256 && tar -xzf mac-20261026T123626Z.tar.gz    # macOS 用 shasum -a 256 -c

端口与地址取自 deploy.env 的 SSH_PORT / SERVER_IP；服务器登录用户默认 root，用 SSH_LOGIN_USER 覆盖。客户端侧的导入与验收见 第 5 页。

收尾会检查已导出的客户端配置是否还对得上服务器。脚本比对 clients/*.json 里的 tls.reality.public_key、short_id 与 Hysteria2 混淆密码，与 deploy.env 不一致的设备会被点名并要求重新 export：这类配置连不上，客户端只报 reality verification failed。重跑 secrets 默认不再轮换这些密钥（见 第 2 页的重跑与换密钥），只有显式给 --rotate-secrets 才会变。
