## 服务器选型：延迟 ≤500ms 的关键在线路，不在配置

自建代理的延迟主要由**中国大陆到 VPS 的物理线路质量**决定，服务器 CPU/内存反而是次要因素。代理中转不需要高配置，1 核 1G 足够。

### 线路优先级

| 线路等级 | 中国大陆典型延迟 | 晚高峰表现 | 月付参考 |
|---|---|---|---|
| **CN2 GIA** | 30–55ms（北京/上海/广州） | 波动通常控制在 10ms 以内 | $30–50+ |
| **CN2 GT / AS9929 / CMIN2** | 70–130ms | 白天优秀，晚高峰可能波动 | $10–25 |
| **普通 163 / 国际 BGP** | 130–200ms | 晚高峰拥堵明显，丢包上升 | $3–10 |

**500ms 的延迟预算非常宽裕**。即使选择美西普通优化线路，晚高峰中美节点 VLESS Reality 的延迟实测约 **160–220ms**，Hysteria2 约 **155–200ms**，都远低于 500ms 上限。如果追求极致稳定和低抖动，优先选 **CN2 GIA** 或 **AS9929/CMIN2** 级别的优化线路；如果预算有限，**美西 CN2 GT / 普通优化线路 + Hysteria2** 也足以把日常使用延迟控制在 200ms 左右。

### 厂商选项

- **稳定优先、预算充足**：**搬瓦工（BandwagonHost）CN2 GIA** 或 **DMIT 洛杉矶/香港 Pro 系列**，两者在社区中被反复提及为“稳定优先”的默认选项。搬瓦工的优势是 KiwiVM 后台支持机房迁移，可以在洛杉矶 CN2 GIA、香港、日本之间切换测试实际线路质量。
- **亚洲低延迟、成本敏感**：**ByteVirt** 等提供月付 $2.5 起的 CN2 GIA / 日本软银线路选项，适合作为低成本起步或备用机。但低价亚洲优化机的带宽和流量通常有限，需要确认晚高峰是否被过度超售。
- **需要原生 IP 属性**：**AkileCloud** 的部分产品强调原生 IP 与流媒体解锁，适合对 IP 注册地属性有明确要求的场景。但“原生 IP”不等于“住宅 IP”，仍需实测 IPQualityScore 分数。

**避坑要点**：尽量选择支持**按小时计费**或**可更换 IP** 的厂商。自建代理的 IP 被封是概率事件，按小时计费可以低成本试错，新开服务器即换新 IP，比年付锁死在一台机器上灵活得多。

## 协议与入口：Hysteria2 为主，VLESS Reality 为备

两个协议解决的问题不同，**组合使用**比只押注一个更符合“稳定性优先”。

### Hysteria2：日常主入口，弱网和晚高峰表现更稳

Hysteria2 基于 **QUIC/UDP**，使用 Brutal 拥塞控制。它的关键特性是：**不把丢包简单视为拥塞信号**，在存在丢包或抖动的链路上更容易维持吞吐，因此适合晚高峰、移动网络、跨境线路质量波动的情况。

实测数据也支持这一点：中美节点晚高峰 Hysteria2 延迟约 **155–200ms，波动较小**；而 VLESS Reality 在同一场景下约 **160–220ms**，且可能因丢包触发重传导致抖动更大。如果你的朋友主要痛点是“高峰期延迟飙升”，Hysteria2 作为主入口是更匹配的选择。

**代价**：Hysteria2 完全走 UDP。部分校园网、公司网络或某些运营商可能对 UDP 有限制或 QoS，此时需要备用入口。

### VLESS Reality：抗封锁更强，UDP 受限时的兜底

VLESS Reality 走 **TCP/443**，握手伪装成访问真实外部网站（如 Apple、Microsoft 的 TLS 握手），对 DPI 和主动探测的隐匿性目前仍是第一梯队。它的优势场景是：**UDP 被封锁或严重限速，以及需要“看起来像正常 HTTPS”的严格网络环境**。

在约 700 万次连接探测的数据中，Hysteria2 成功率 99.6%，VLESS Reality 97.8%——Reality 成功率略低并不代表它更差，而是两者承担的网络场景不同；单一协议在行为层面的检测面前更容易暴露，**多协议多样性本身就是一种容错**。

### 推荐组合

> **Hysteria2 作为默认日常出口；VLESS Reality 作为 UDP 不可用或 Hysteria2 被干扰时的备用入口。**

在 sing-box 中，两个入站可以同时运行在同一台 VPS 上，客户端侧根据网络环境切换或由 URLTest 自动选择。

## 全平台客户端：sing-box 统一配置

**sing-box 官方原版核心**可以用一份 JSON 配置覆盖 Linux、Windows、macOS、Android 和 iOS，这是实现“全平台可用”且规则一致的最直接路径。

| 平台 | 客户端形态 | 关键设置 |
|---|---|---|
| **Android** | sing-box 官方 App 或 NekoBox | 开启 TUN 模式，导入 JSON 配置 |
| **Windows** | sing-box 命令行 + GUI 前端（如 sing-box GUI） | 开启 TUN，首次需要管理员提权 |
| **macOS** | sing-box GUI 或命令行 | 开启 TUN，系统扩展授权 |
| **iOS（如需）** | sing-box 官方 App | 同一份配置可直接导入 |

**TUN 模式**是实现“全局代理/规则代理”无缝切换的基础：开启后，操作系统层面所有流量都会经过 sing-box，再由路由规则决定走代理、直连还是拒绝。

## 分流设计：规则代理与全局代理的统一实现

sing-box 的路由模块可以将入站流量按规则分发到不同出站，天然支持**规则代理**和**全局代理**两种模式。推荐使用 **rule_set 远程规则集** 方案，而非写死静态 IP/域名列表，这样规则可以跟随上游更新，减少维护成本。

### 推荐路由结构

```
入站（Hysteria2 / VLESS Reality）
        │
        ▼
  路由决策
   ├── 私有地址 / 中国大陆 IP → direct（直连）
   ├── geosite:cn → direct
   ├── OpenAI / ChatGPT / Gemini 域名 → AI-Outbound
   │        ├── 优先：WARP 出站
   │        └── 备用：固定 SOCKS5 出口
   ├── Google / YouTube → 主代理出站（Hysteria2）
   └── 默认 → 主代理出站
```

- **规则代理**：将 `geosite:cn`、`geoip:cn`、私有地址段设为 `direct`，避免国内流量绕行海外。
- **全局代理**：在客户端将 `final` 出站指向代理，或在 GUI 中直接切换为 global 模式。sing-box 本身不强制区分“模式”，本质是改 `final` 或规则集优先级。
- **AI 域名单独路由**：这是下面 IP 纯净度部分的核心操作。OpenAI 相关域名至少应包含 `openai.com`、`chatgpt.com`、`oaistatic.com`、`oaiusercontent.com`、`auth.openai.com` 等，sing-box 也可以直接使用编译好的 `geosite:openai` 规则集。

## IP 纯净度高于 80% 的工程做法

“纯净度 80%”没有统一官方定义，但可以用可测量的指标来逼近。工程上建议从**入口 IP 筛选**和**AI 出口解耦**两个层面处理。

### 用 IPQualityScore 量化筛选

在购买 VPS 后、正式部署前，用 IPQualityScore 检测目标 IP 的 **Fraud Score（0–100）**：**0–20 为干净，20–50 为可疑，50+ 为高风险**。将“Fraud Score ≤20”作为购买/保留机器的硬性筛选条件，就相当于在可测量口径上把“纯净度 ≥80%”落到了实处。也可以用 `ippure.cc` 的终端命令快速查看网络类型：**住宅（Residential）信誉最高，企业专线次之，IDC 机房 IP 风控权重最高**。

### 关键认知：机房 IP 很难同时做到“便宜 + 高信誉 + AI 全解锁”

绝大多数低价优化线路 VPS 的 IP 属于 **IDC/数据中心属性**，在 ChatGPT、Claude 等服务的风控中天然处于劣势。即使 Fraud Score 较低，AI 服务仍可能因为 IP 段属性触发挑战或限制。因此，**不要把 AI 流量的可用性完全押在 VPS 的本机 IP 上**。

### 推荐：AI 流量单独走 WARP 或固定 SOCKS5

实际工程中更稳妥的结构是：

> **Hysteria2 / VLESS Reality 作为统一入口 → 普通流量直出 VPS 本机 IP → OpenAI/ChatGPT/Gemini 流量单独走 Cloudflare WARP 出站 → 需要稳定 Claude 出口时再叠加固定 SOCKS5。**

这样做的逻辑是：把 **AI 服务的出口** 与 **廉价 VPS 的原生机房 IP** 解耦。WARP 不需要接管整台 VPS，只需在 sing-box 中为 AI 域名指定一个独立的 `wireguard` 出站即可。这样 YouTube/Google 仍然走 VPS 本机带宽（速度更快），而 ChatGPT 等风控敏感服务走另一条出口，某一条路径出问题时更容易定位和替换。

## 稳定性兜底清单

在部署完成后，以下几项操作对“延迟稳定可控”的收益最直接：

1. **启用 BBR**：在 VPS 上设置 `net.core.default_qdisc=fq` 和 `net.ipv4.tcp_congestion_control=bbr`。BBR 在丢包发生时仍能最大化利用带宽，是跨境代理场景的基础优化。
2. **优先 Hysteria2 应对晚高峰**：如果晚高峰的主要痛点是丢包和抖动，Hysteria2 的 Brutal 拥塞控制比单纯依赖 TCP BBR 更能在弱网下维持体验。
3. **保留可更换 IP 的能力**：选择按小时计费或明确支持换 IP 的厂商；IP 整段被封时，换协议无效，只能换 IP 或换线路。
4. **VLESS Reality 备用入口常驻**：不一定要日常使用，但在 UDP 被 QoS 或 Hysteria2 握手异常时，它提供一条 TCP/443 的“看起来像正常 HTTPS”的通道。
5. **DNS 防泄露**：在 sing-box 中配置独立的 DNS 出站，避免直连 DNS 查询暴露代理意图，也避免 DNS 污染导致分流规则误判。

**一句话总结**：以一台 **CN2 GIA / AS9929 级别优化线路 VPS** 为底座，**Hysteria2 为主、VLESS Reality 为辅**构成双入口，用 **sing-box 全平台 TUN + rule_set** 实现规则/全局分流，**AI 域名单独路由到 WARP 或固定 SOCKS5 出口**，再用 **IPQualityScore Fraud Score ≤20 + BBR** 做入口筛选和传输层兜底。这套结构在延迟上远低于 500ms 预算，在 IP 策略上把“入口干净”和“AI 出口可用”分开管理，比把所有需求压在一台机器的单一 IP 上更可控。
