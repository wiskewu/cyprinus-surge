3 · 服务端配置与自检

目标：把第 2 步生成的参数渲染成 sing-box 配置、启动服务，再用自检脚本确认监听、日志、证书都对。读者是维护这台节点的人。

cd /root/deploy
bash bin/deploy/one/server.sh
bash bin/deploy/check/server.sh

bin/deploy/one/server.sh 用 deploy.env 渲染配置 → sing-box check 校验 → 重启服务。校验不通过就不会覆盖旧配置。

bin/deploy/check/server.sh 输出 10 项检查，全绿再往下走。各项含义见 排查手册。

设备名单

bin/deploy/one/secrets.sh 顺便建了 /etc/sing-box/devices.list，第一台叫 main。服务端的 users 数组就是从它渲染的，所以改名单 → 重跑 bin/deploy/one/server.sh 就生效。

# 名字 凭据 平台：一台设备一行
main   af2358a4-df32-419c-9774-63a44c540970  desktop
phone  9b2c1d70-3e44-4a1b-8c02-7e5d9f10a333  android

一台设备一个凭据，同时当 VLESS 的 uuid 和 Hysteria2 的 password 用，所以删一行就是吊销那台，两条入口同时失效，不会漏一边。

这份名单就是全部设备的凭据。别提交到公开仓库：要版本管理就放私有仓库或加密后存；随手的本地副本用完删掉。
改凭据请用 bin/deploy/device.sh，别手改名单：它会顺手重渲染服务端并重新生成那台的客户端配置。

常用

DRY_RUN=1 bash bin/deploy/one/server.sh   # 只生成配置，不动系统
systemctl status sing-box
journalctl -u sing-box -n 50 --no-pager
systemctl restart sing-box

加固：降权与 systemd 沙箱 推荐

默认的单元文件让 sing-box 以 root 全权限运行。它是唯一监听公网、解析密文的进程，值得收一次权限。脚本幂等，随时可以 --check 复查或 --revert 退回。

一键脚本把这一步作为 harden 步骤固定执行，位于 hy2 之后、porthop 之前，不需要单独跑。单独重装 sing-box 之后补一次 bash deploy.sh --only harden --overwrite --yes。

sudo bash bin/deploy/one/harden.sh           # 建 system 用户、收权限、重写 unit、重启并自检
sudo bash bin/deploy/one/harden.sh --minimal # 只降权，不加沙箱指令
sudo bash bin/deploy/one/harden.sh --check   # 只看现状
sudo bash bin/deploy/one/harden.sh --revert  # 用备份的 .orig 覆盖回去并重启
做了什么为什么
User=sing-box + CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_BIND_SERVICE CAP_NET_RAW只需要三项能力：操作 nftables/路由、绑 443、创建 TUN。其余 root 权限一律不给
/etc/sing-box 归 root:sing-box，目录 750、文件 640配置里有 REALITY 私钥与证书私钥，只有该组可读
ProtectSystem=strict、ProtectHome、PrivateTmp、ReadWritePaths=/var/lib/sing-box文件系统只读，唯一可写是自己的运行目录
ProtectKernelTunables、ProtectKernelModules、ProtectKernelLogs、ProtectControlGroups、ProtectClock、ProtectHostname、ProtectProc=invisible内核面全部收掉，nftables 走 netlink 不受影响
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_NETLINK、RestrictNamespaces、MemoryDenyWriteExecute、SystemCallFilter=@system-service只留网络相关的地址族与系统调用

怎么算加固成功

脚本的判定不是「服务 active」就算过。sing-box 起来后还要几十到几百毫秒才绑定端口，只看 unit 状态会把「还在绑定」误判成失败，因此它会等端口：服务 active 且 VLESS_PORT 在监听，启用 Hy2 时再要求 HY2_PORT/udp 在监听，最多等 20 秒。任一条件不满足就回滚。

sudo bash bin/deploy/one/harden.sh --check

关键三行：生效 User 应为 sing-box、StateDirectory 应为 sing-box、沙箱 应为 完整。另有两行用来排除干扰：FragmentPath 与 DropInPaths，后者不为空说明有 drop-in 覆盖了单元。

重渲染会把配置权限改回 600 root:root。降权后 sing-box 读不到，表现为 read config at …: permission denied。渲染脚本已改用 install_service_file，按单元里的 User= 自动落成 640 root:<该用户的组>；手工 install -m 600 覆盖过配置的，补 chgrp 后重启即可。
排障时先对齐时间。按行数取日志会把历史失败一起打出来，几小时前的 FATAL 看起来像刚发生的。做法见排查手册的「重启竞态」。

沙箱下起不来时怎么定位

脚本会在重启后自检，失败自动回滚到 .orig，原服务照旧运行。原因看 journal 里的 status=：

journalctl -u sing-box -n 50 --no-pager
status=含义先删哪一组
226/NAMESPACE某项命名空间或文件系统隔离加不上先去掉 ProtectSystem=strict、ProtectHome、PrivateTmp，逐条加回
203/EXEC执行阶段就被拒：二进制路径、权限或能力不够先跑 --minimal，确认没有 User= 与能力集的问题
降权后 chdir … permission denied/var/lib/sing-box 还是 root:root 700，sing-box 用户进不去ls -ld /var/lib/sing-box 应显示 sing-box sing-box；脚本已显式 chown，并用 StateDirectory 让 systemd 兜底
回滚后仍 chdir … permission denied原单元以 root 运行，但能力集里没有 CAP_DAC_OVERRIDE，root 不绕过文件权限；目录属主是 sing-box，root 成了「其他人」，750 的 o 位没有 xchown -R root:root /var/lib/sing-box && chmod 700 /var/lib/sing-box；bin/harden/harden.sh --uninstall 与自动回滚都已包含这一步
1 且日志有 permission denied配置、证书或运行目录读不到ls -l /etc/sing-box 看是否 root:sing-box、目录 750、文件 640
1 且日志有 operation not permitted系统调用被 SystemCallFilter 拦下去掉 SystemCallFilter 与 SystemCallErrorNumber

二分顺序：先 --minimal 确认降权本身没问题，再加回文件系统组，最后加进程组。也可以用 sudo bash bin/deploy/check/selfcheck.sh：它对每组属性做一次带真实二进制的试验，直接指出是哪一组挡住启动；--fix-dac 按生效用户修正目录属主，--recover 退回原单元。加回时一次只放一组，每轮都看 systemctl is-active 与 ss -tlnp。

只看日志用 --no-pager。在极简终端里直接跑 journalctl 会进分页器并提示 WARNING: terminal is not fully functional，那不是服务报错。
改完会重启 sing-box。脚本重启后验证「服务 active + VLESS_PORT 在监听 + 启用 Hy2 时 HY2_PORT/udp 在监听」，任一不满足就自动回滚到原单元。若在沙箱下起不来，多半是某个 Protect* 或 SystemCallFilter 挡了 TUN 与 netlink：删掉对应一行再跑。
原单元备份在 /etc/systemd/system/sing-box.service.orig，只在首次加固时写一次，重复执行不会覆盖它。用 bin/deploy/one/install-singbox.sh 重装 sing-box 会把 unit 覆盖回未加固版本，重装后需要再跑一次本脚本。

设备管理

bin/deploy/device.sh 在服务器上就地完成：改名单 → 重渲染服务端 → 重新生成那台的客户端 JSON，然后你把 JSON 拿去分发。它不自己实现任何 sing-box 逻辑，渲染一律走现有脚本，所以不会和模板漂移。

sudo bash bin/deploy/device.sh list
sudo bash bin/deploy/device.sh add laptop [desktop|android|ios]   # 默认 desktop
sudo bash bin/deploy/device.sh rotate laptop                       # 换凭据，旧配置立刻失效
sudo bash bin/deploy/device.sh revoke laptop                       # 删掉，两条入口同时失效
sudo bash bin/deploy/device.sh render laptop                       # 只重渲染客户端配置
sudo bash bin/deploy/device.sh export laptop                       # 渲染并打包，附校验和

产物在 /etc/sing-box/clients/sing-box-client-<名字>-<平台>.json：

scp root@服务器:/etc/sing-box/clients/sing-box-client-laptop-desktop.json laptop@机器:~/
每台设备只发它自己那一份。整个 devices.list 落到任何一台机器上，就等于把所有设备的凭据都给了它。名单本身也要进 .gitignore 或单独加密存放。
add / rotate / revoke 都会重启 sing-box。当前活跃会话不会断（连接已建立），但新连接会短暂受影响。
这里的名字只属于代理凭据。SSH 的密钥与吊销走另一套机制，与 devices.list 无关，见 SSH 加固手册。

跑完之后做什么

  1. 确认产物：ls -l /etc/sing-box/clients/。文件名里的平台就是这台设备的平台。
  2. 只发那一份：上面那条 scp。客户端机器不需要 client.env、devices.list 或密钥包。
  3. 导入：按平台操作见 第 5 页的导入表；Android 用 -android.json，iOS 用 -ios.json。
  4. 验收：在客户端机器上（不带 client.env，只给两个变量）：
    SERVER_IP=你的服务器IP VLESS_PORT=443 bash bin/deploy/client/verify.sh
    见 第 6 页。
  5. 以后要换/要删：rotate → 重新 scp → 客户端重新导入（旧 JSON 的凭据当场失效）；revoke 之后需删除对方机器上的那份 JSON。换设备不改名单时，客户端那份旧 JSON 照样能用。

一台机器要出多份（比如笔记本同时要桌面与安卓版）：凭据按名字算，建两条各管一个平台，各自能单独吊销。

sudo bash bin/deploy/device.sh add laptop desktop
sudo bash bin/deploy/device.sh add laptop-android android
