1 · 隧道与系统代理残留

停掉 TUN 客户端之后仍然上不了网。真实原因是两件事叠在一起：隧道由系统扩展持有，图形界面退出不等于断开；网络服务上还挂着指向某个本地端口的系统代理。

现象

观察当时的实际状态
终端里 curl https://www.baidu.com200，正常
浏览器与多数图形界面程序提示「无法连接互联网」
ifconfig utun0 之类的隧道网卡时有时无，客户端退出后仍残留
客户端图标是否出现在程序坞已经退出，进程表里也查不到对应进程

这组现象同时出现时，不要往「网络坏了」方向查。命令行通而图形界面不通，问题必然在应用层读取的配置上，要么代理，要么 DNS。

排查顺序

  1. 先证明系统层是通的。命令行工具默认不读系统代理，它通就说明链路没问题：

    curl -m 8 -sS -o /dev/null -w '%{http_code}\n' https://www.baidu.com
dig +short www.baidu.com | head -3

  2. 看谁持有默认路由与 DNS。隧道网卡存在时，默认路由与解析器都会指向它；网卡消失后应当自动回落到物理网卡：

    netstat -rn -f inet | awk '$1=="default"'
route -n get 8.8.8.8 | grep interface
scutil --dns | grep -m2 nameserver
ifconfig | grep -E '^utun[0-9]+:' -A3 | grep inet

  3. 判断隧道宿主是不是图形界面进程。基于 Network Extension 的客户端把核心装在系统扩展里，退出 App 不会断开隧道：

    systemextensionsctl list
ps ax -o pid,user,etime,comm | grep -i PacketTunnel
scutil --nc list

  4. 再看系统代理落在哪个网络服务上。这一步是本次的根因，且 scutil --proxy 可能读不到实时值，用 networksetup：

    for s in $(networksetup -listallnetworkservices | tail -n +2); do
  printf '%s: ' "$s"
  networksetup -getwebproxy "$s" | tr '\n' ' '; echo
done
networksetup -getsecurewebproxy  "Wi-Fi"
networksetup -getsocksfirewallproxy "Wi-Fi"

结论一：退出图形界面不会断开隧道

客户端注册的是一个 NetworkExtension 服务，隧道由系统扩展进程以 root 身份运行，由系统的会话管理器托管。图形界面只是配置面板，退出它之后 scutil --nc list 里那条记录仍然是已连接状态，隧道网卡、默认路由、TUN 内 DNS 全部照旧。

# 列表里对应的服务名来自客户端注册的 VPN 配置，用你自己的那个名字
scutil --nc stop "<服务名>"

ifconfig | grep utun                       # 隧道网卡应消失
route -n get 8.8.8.8 | grep interface      # 应回落到物理网卡
scutil --dns | grep -m2 nameserver         # 不应再有隧道内的解析器

要长期关掉，在「系统设置 → 通用 → 登录项与扩展 → 网络扩展」里取消勾选该扩展；彻底移除用 sudo systemextensionsctl uninstall <teamID> <bundleID>，参数取自 systemextensionsctl list。代价是这类客户端在没有扩展时无法建立隧道，等于不可用。

结论二：系统代理残留在网络服务上

另一个客户端的系统代理设置被写进了当前 Wi-Fi 服务，指向它自己的本地混合端口。那个客户端早已退出，端口无人监听，于是所有读取系统代理的程序（浏览器、聊天工具、应用内更新）一律连不上；curl 不读系统代理，所以一切正常。

# 关掉三条代理设置，需要管理员授权
sudo networksetup -setwebproxystate        "Wi-Fi" off
sudo networksetup -setsecurewebproxystate  "Wi-Fi" off
sudo networksetup -setsocksfirewallproxystate "Wi-Fi" off

networksetup -getwebproxy "Wi-Fi"           # 应为 Enabled: No

图形界面的等价操作是「系统设置 → 网络 → Wi-Fi → 详细信息 → 代理」，把三个开关关掉。改完重启浏览器，系统代理是在进程启动时读取的。

三个容易误判的点

curl 不读系统代理。它只看环境变量里的代理配置。用它验证「网络是否通」是对的，用它验证「浏览器为什么不通」一定会跑偏。要复现浏览器处境，显式指定代理：curl -x http://127.0.0.1:<端口> ...。
--interface 只绑源地址，不改路由。默认路由仍在隧道时，curl --interface en0 照样走隧道。判断真实出处只有两条：route -n get <IP> 的 interface 字段，或者把隧道摘掉再测。
scutil --proxy 不是判据。网络服务上的代理项存在时它也可能显示为空，因为它读的是已发布的偏好状态。查代理一律用 networksetup -get*proxy。

退出客户端后的验收清单

三条全部满足才算收拾干净，缺一条就会在某个程序上表现为「没网」：

ifconfig | grep -E '^utun[0-9]+:' -A3 | grep inet     # 无输出
route -n get 8.8.8.8 | grep interface                 # 物理网卡
networksetup -getwebproxy "Wi-Fi"                     # Enabled: No
scutil --dns | grep -m2 nameserver                    # 物理网卡的 DNS

避免复发

  • 同一时间只留一个出口。两个客户端并存时，一个走 TUN 抢路由，另一个往网络服务里写系统代理，故障现象会互相掩盖。
  • 用客户端的「断开连接」，不要用「退出」。有的客户端退出时会还原系统代理，被强杀或崩溃时不会；不可依赖，退出后照着上面的清单核一遍。
  • 把兜底策略改成直连。TUN 客户端的路由规则若把 final 指向节点，隧道一断就是全断，连国内站点都受影响。规则里让国内域名与常用站点走 direct，只把需要代理的域名指到节点，隧道故障就降级为「部分站点不可用」。
