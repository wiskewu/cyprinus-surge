三个容易忽略的点

sleep 2 在等什么

ProxyCommand 里的 sleep 2 不是凑数。它等的是 fwknopd 把 iptables 规则插进去。UDP 到了 → 验签 → 写规则，这几步要时间；nc 抢在前面连，22 还是关着的。

ProxyCommand fwknop -n server1 >/dev/null 2>&1; sleep 2; nc %h %p

两个细节：

  • >/dev/null 2>&1 是必须的。ProxyCommand 的 stdout 会被 ssh 当成加密通道来读，fwknop 的任何输出都会污染这条流。
  • 用 ; 而不是 &&。新机器上 fwknop 还没装时敲门会失败，但 nc 照样往下走——那时 22 还开着，正好用同一条命令兼容「装之前」和「装之后」两种状态。

UDP 会丢，所以可以重敲

SPA 走 UDP，可能在链路上丢包。fwknop 是无状态的：重复发同一个包没有副作用。SSH 卡住就再敲一次，不用等窗口过期，也不用担心「敲多了会被限速」。

规则撤销不等于断线

窗口到期撤销的是放行规则，也就是「允许建立新连接」。已经建立并认证过的会话由内核的连接跟踪维持，不受影响。所以一条 120 秒的规则足够开一次交互式登录，但如果你要挂长时间会话，得把 ACCESS_TIMEOUT 调大后重跑服务端脚本。

把图 3 压成一句话：绝大多数时间都停在「关闭」，此时 22 上没有任何放行规则；只有一个很短的窗口里有。

验签失败是静默的。攻击者无法区分「密钥错了」和「包里根本没有密钥」——两种情况都不回错误包。这条性质让暴力猜密钥在协议层就没有反馈，不依赖限速。

防重放靠三样东西

包里带时间戳和一次性序列号，服务端渲染的配置把它们都打开：

ENABLE_SPA_PACKET_AGING  Y;    # 拒绝时间戳过旧的包
MAX_SPA_PACKET_AGE       120;  # 判定「过旧」的秒数
ENABLE_DIGEST_PERSISTENCE Y;   # 摘要缓存跨进程重启保留

最后一条容易被忽略：如果 fwknopd 重启就忘了见过哪些摘要，攻击者可以在重启后重放旧的包。开启后缓存落盘，重启不影响防重放。

客户端配置长什么样

20-client.sh 生成的内容（主机名和密钥为示意）：

[default]
SPA_SERVER_PROTO  udp
USE_HMAC          Y
HMAC_DIGEST_TYPE  SHA512
ALLOW_IP          resolve        # 自动探测公网出口 IP
ACCESS            tcp/22         # 我要开哪个端口
KEY_BASE64        <这台设备的加密密钥>
HMAC_KEY_BASE64   <这台设备的 HMAC 密钥>

[server1]
SPA_SERVER        203.0.113.10
SPA_SERVER_PORT   62201

[server2]
SPA_SERVER        198.51.100.7
SPA_SERVER_PORT   62201

加密密钥和 HMAC 密钥必须分开：一个负责内容保密，一个负责身份认证，混用会削弱整套方案的性质。ALLOW_IP resolve 需要能访问外网（fwknop 查公网 IP 的服务）；固定 IP 的机器可以在 [default] 里写死 ALLOW_IP <你的IP>。
