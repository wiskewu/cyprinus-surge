故障速查

现象查什么
ssh 直接超时服务端 journalctl -u fwknop-server -n 50；客户端 fwknop -n <host> -v。UDP 被中间设备丢了 → 重敲一次
敲门后仍连不上iptables -S FWKNOP_INPUT 看规则插上没有；iptables -S INPUT | grep FWKNOP_INPUT 看跳转还在不在（多半是 ufw reload 过）
客户端报「stanza not found」~/.fwknoprc 里没有 [<主机名>] 段。fwknop 装完会丢一个全注释的同名样例文件，脚本会先备份成 ~/.fwknoprc.bak
客户端报密钥相关错误服务端和客户端密钥对不上。多半是客户端装 fwknop 时自带的样例 ~/.fwknoprc 覆盖了生成的版本
服务端 fwknopd 起不来fwknopd -F 前台跑看报错。常见是 access.conf 里混进了空格或中文标点
nmap 显示 22 是 closed 而非 filtered还有别的东西在放行 22：云厂商安全组、ufw 的其他规则、还有 /etc/hosts.allow 之类
日志里没有 SPA 记录包根本没到。服务端 tcpdump -i any udp port 62201 确认；没有就是服务商封了 UDP 或非标端口
客户端卡在 resolveALLOW_IP resolve 需要能访问外网。固定 IP 的机器在 [default] 里写死 ALLOW_IP <你的IP>

与 ufw 的关系

fwknopd 自己往 FWKNOP_INPUT 链插规则，跳转规则插在 INPUT 的第 1 位：

IPT_INPUT_ACCESS   ACCEPT, filter, INPUT, 1, FWKNOP_INPUT, 1;
#                                        ↑ 位置 1，先于 ufw 的链求值

所以 SPA 开的口子不会被 ufw 挡掉。代价是 ufw status 里看不到这些临时规则——它不知道 fwknopd 存在。

最大的坑：ufw enable / ufw reload / ufw reset 会重建 INPUT 链，把跳转规则冲掉。之后 SPA 静默失效——客户端不报错，fwknop 正常发包，SSH 直接超时。任何 ufw 变更之后：
sudo systemctl restart fwknop-server     # 让它把跳转插回去
10-server.sh 每次改完 ufw 都会自动重启一次。

检查跳转还在不在

iptables -S INPUT | grep FWKNOP_INPUT     # 有输出 = 正常（在第 1 位）
sudo bash 10-server.sh --status

嗅探端口

服务端默认只嗅探 udp port 62201（PCAP_FILTER）。客户端用了 fwknop --rand-port 就打不进来，得把这一行放宽：

PCAP_FILTER   udp dst portrange 10000-65535;

更省事的做法是别用随机端口。改完重启 fwknop-server。

并行接入通道

建议在同网（如 Tailscale / WireGuard 的 tailscale0）上再留一条不经敲门的路：

sudo ufw allow in on tailscale0

它的作用不是「fwknop 坏了的备份」，而是一条独立存在的路：公网配置写错了，你仍然能从 tailnet 进去修。VPS 上的 Tailscale 本身也吃 SSH 规则，所以这两件事是配套的。

Docker 的影响

Docker 启动时会重写 FORWARD 和 nat 链。fwknopd 的跳转在 INPUT 上，理论上不受影响，但如果发现 SPA 时好时坏：

iptables -S INPUT | head -5          # 确认跳转还在第 1 位
sudo systemctl restart fwknop-server # 重插一次

已知限制

  • 不是万能。SPA 挡的是「没钥匙的人连不上 sshd」。OpenSSH 自身的 0day 依然要靠及时打补丁；拿到密钥的中间人攻击依然成立。它改变的是暴露窗口。
  • 密钥就是命门。密钥泄露 = 22 端口随时对攻击者开放，而且不会有任何异常日志——在他看来就是一次合法敲门。
  • 需要 UDP 出境。对 UDP 严格管控的网络（部分校园网、公司网）里 62201/udp 可能不通，SPA 反而挡了你的路——那种环境本来就该走别的路。
  • 服务商可能封 UDP 或非标端口。被封的表现和「客户端丢包」一模一样，先在服务端 tcpdump 确认包到没到。
  • 并发受限。每台设备每次敲门生成一条规则；同一个 IP 短时间内多次敲门会累积多条规则，靠 iptables 的超时清理。MAX_FW_TIMEOUT 封顶就是防止客户端给自己开超长窗口。
  • 脚本按 Debian/Ubuntu 写（apt + ufw + systemd；服务端包 fwknop-server、客户端包 fwknop-client）。其他发行版照着改；客户端脚本已额外支持 brew / pacman。
