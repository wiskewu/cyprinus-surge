4 · 部署

三个脚本，彼此独立，可以分别在不同机器上跑。全部幂等：改完配置重跑即可，不会留下半成品。

把脚本传上去

scp -r docs/quality/scripts root@<服务器>:/root/ssh-spa     # 或者只 scp 你要用的那一个

第 1 步 · 生成密钥

在你自己安全的机器上跑，不要在服务器上生成：

bash 00-gen-keys.sh --hosts "server1=203.0.113.10 server2=198.51.100.7" --clients "laptop phone"

产出 spa-keys.env（服务端，含全部设备）+ clients/{laptop,phone}.env。详见 第 2 页。

第 2 步 · 服务端

scp spa-keys.env root@<服务器>:/root/
ssh root@<服务器> 'bash /root/ssh-spa/10-server.sh --keys /root/spa-keys.env'

按顺序做了五件事：

  1. 装 fwknop-server（Debian 包名，客户端才是 fwknop-client）
  2. 渲染 /etc/fwknop/fwknopd.conf：按默认路由网卡写 PCAP_INTF，嗅探端口取 SPA_PORT，跳转规则放在 INPUT 第 1 位，防重放三项全开。包自带版本备份为 fwknopd.conf.orig
  3. 渲染 /etc/fwknop/access.conf（0600）：从密钥包逐个 stanza 展开，并自检 stanza 数 == 密钥组数
  4. 探测 SSH 端口：四路（当前连接 → ss 监听 → ssh.socket 的 ListenStream → sshd_config），不假设是 22。云厂商给的新机器常是随机端口，按 22 去操作会关错；sshd 同时监听多个端口时每一个都会处理
  5. 启动 fwknop-server：起不来就打日志退出，此时防火墙还没动；起来了还要确认 FWKNOP_INPUT 跳转真的插上了
  6. 防火墙：ufw allow 62201/udp，SSH 端口保持原样；改完 ufw 后自动重启一次 fwknopd（见 第 5 页）
  7. 把探测到的端口写回密钥包：客户端配置里的 ACCESS tcp/<端口> 必须和服务端一致，而密钥包是在别的机器上生成的。你分发给客户端的应当是跑完这一步之后的那份
渲染出来的 fwknopd.conf
PCAP_INTF                eth0;
PCAP_FILTER              udp port 62201;

FLUSH_IPT_AT_INIT        Y;
FLUSH_IPT_AT_EXIT        Y;
ENABLE_IPT_COMMENT_CHECK Y;

# 防重放：时间戳 + 摘要缓存（进程重启后仍认得旧包）
ENABLE_SPA_PACKET_AGING  Y;
MAX_SPA_PACKET_AGE       120;
ENABLE_DIGEST_PERSISTENCE Y;

# 跳转规则插在 INPUT 第 1 位，因此在 ufw 的链之前求值
IPT_INPUT_ACCESS         ACCEPT, filter, INPUT, 1, FWKNOP_INPUT, 1;
ENABLE_IPT_FORWARDING    N;
ENABLE_IPT_SNAT          N;
ENABLE_IPT_OUTPUT        N;
ENABLE_IPT_LOCAL_NAT     N;

SYSLOG_ID                fwknopd;

第 3 步 · 客户端

每台机器各跑一次，只给它自己那一份密钥：

scp clients/laptop.env <你的机器>:~/
ssh <你的机器> 'bash 20-client.sh --keys ~/laptop.env'

做了三件事：装 fwknop；写 ~/.fwknoprc（0600）；往 ~/.ssh/config 追加一个托管块。

~/.fwknoprc 里关键的是 ALLOW_IP，默认写 source：SPA 包里写 0.0.0.0，服务端按「包从哪个 IP 来」放行——不需要 wget，也不怕你换网络。需要时在密钥包里加一行 ALLOW_IP=… 覆盖：

取值客户端要什么适合
source（默认）什么都不用漫游、家宽 IP 会变。代价：fwknop 官方认为比写死 IP 弱一档（包的价值在「谁发出」）
resolvewget（macOS 默认没有：brew install wget）能装 wget、想抗 MITM
<你的公网IP>什么都不用固定 IP（家里的宽带、办公室）
ProxyCommand 必须包一层 /bin/sh -c。ssh 会把 ProxyCommand 改写为 exec <命令> 再执行，所以 exec fwknop …; sleep 2; nc … 里的 sleep / nc 永远不会执行——症状是握手之前就 EOF：Connection closed by UNKNOWN port 65535，看起来像 SPA 或端口问题，其实转发程序压根没启动。正确写法：
ProxyCommand /bin/sh -c 'fwknop -n <别名> >/dev/null 2>&1; sleep 2; exec nc %h %p'
（脚本已按这个写。手工改过配置的一定要对照一下。）
服务器登录名和本地用户名不一致时，一定要给 --user。托管块里没有 User 的话，ssh 会拿本机用户名去登录（比如 wangyao），而这台机器上可能只有 root——报错是 Permission denied (publickey)，很像「SPA 又坏了」。
bash 20-client.sh --keys ~/mac.env --user root
托管块是幂等的。带 # BEGIN ssh-spa … # END ssh-spa 标记，重跑只原地替换并清掉多余空行，不会越堆越多；--uninstall 摘掉之后与原文件逐字节一致。
参数作用
--keys FILE必填。自己那一份密钥包
--name NAME覆盖包里的 CLIENT_NAME
--no-ssh只写 ~/.fwknoprc，不碰 ~/.ssh/config
--status显示当前配置
--uninstall还原 ~/.fwknoprc，删掉托管块

装包路径按顺序探测：brew → apt（fwknop-client）→ pacman。缺 nc 只警告不中止，因为 ProxyCommand 的最后一步要它（Debian/Ubuntu：apt install netcat-openbsd）。

第 4 步 · 收口

顺序不能反。先在当前这个 SSH 会话里另开一个连接，确认能进得来，再收口。
bash /root/ssh-spa/10-server.sh --keys /root/spa-keys.env --close-ssh

它会删除探测到的每一个公网 SSH 端口规则（ufw limit 和 ufw allow 两种都试），然后回读 ufw status 确认规则真的没了——ufw 删一条不存在的规则也返回 0，只看退出码会把「没关上」报成「已关闭」。还有规则残留时脚本直接报错退出。

sshd 若同时监听多个端口，全部都会被处理：只关一个的话另一个还开着，而 SPA 只放行其中之一，等于多开一扇没用的门。

收口前会检测 tailscale0 / wg0 这类并行通道，没有就提醒你收口后只剩云控制台 VNC 能回来（只提醒，不阻止）。

退出（回到不敲门的直连）

不想用了、换机器了、SPA 把你自己卡住了——用 90-uninstall.sh，别手敲 iptables。登录方式、密钥包去留、是否真的拆，都会逐条问，不替你选默认值：

# 服务器：先放行公网 SSH 并回读确认，再停 fwknopd、清跳转、关 SPA 端口、还原配置
sudo bash 90-uninstall.sh              # 交互式，推荐
sudo bash 90-uninstall.sh --check      # 只看现状，什么都不改

# 非交互（脚本、heredoc）：关键步骤必须显式给，缺了就退出
sudo bash 90-uninstall.sh --password no -y                         # 仅公钥
sudo bash 90-uninstall.sh --password yes --root-login yes -y       # 密码登录，root 也能用密码
sudo bash 90-uninstall.sh --password no --purge -y                 # 连 access.conf 与密钥包一起删

# 每台客户端：还原 ~/.fwknoprc，摘掉 ~/.ssh/config 里的托管块
bash 90-uninstall.sh --client
bash 90-uninstall.sh --client --purge --keys ~/mac.env   # 连本地那份密钥包一起删
顺序是安全的关键。收口之后公网 SSH 规则已经不存在，唯一在放行的是 FWKNOP_INPUT 里那条临时规则。90-uninstall.sh 因此先 ufw allow 并回读确认，确认不了就直接退出（此时 SPA 还完整）——绝不在「SSH 没路可走」的状态下先拆 SPA。
参数作用不给会怎样
--password yes|no退出后是否允许密码登录；no 时连 KbdInteractiveAuthentication 一起关（键盘交互式也能送密码）交互式会问；非交互直接退出
--root-login yes|no|prohibit-password只影响 root：prohibit-password = 只允许公钥登 root--password yes 且 root 当前是 prohibit-password 时，非交互直接退出（否则只开密码登录等于没解决）
-y, --yes跳过拆除确认交互式会问；非交互直接退出
--purge连 access.conf 与密钥包一起删交互式会问；默认保留

改的是实际生效的那一行：sshd 对每个关键字只取「第一个出现的值」，而 Include sshd_config.d 会按文件名顺序就地展开。所以 50-cloud-init.conf 里若写着 PasswordAuthentication no，脚本改的就是它，而不是自己那份 99-*.conf。改完 sshd -t 校验、reload，并用 sshd -T 回读确认——对不上就把「谁设的」列出来。

开密码登录＝回到可被爆破的状态。只在你需要换回旧方式、或机器上没有可用公钥时才开；开着就让 fail2ban 继续跑（fail2ban-client status sshd）。只想恢复访问的话，更稳的做法是把新公钥装进 authorized_keys，密码登录保持 no。

还原之后的状态：公网 SSH 直连、不再需要敲门、fwknopd 停用、fwknopd.conf 用回包自带那份。fail2ban 与代理配置不动；客户端的 ~/.ssh/config 里只删带 # BEGIN ssh-spa 标记的那一段，你自己的配置原样保留。

选「仅公钥」而本机又没找到 authorized_keys 时，脚本会在拆之前警告：拆完只剩云控制台能进。

锁门急救

万一还是锁了——云厂商控制台的 VNC / 串口，或者你之前装了 Tailscale（见 第 5 页）。端口按探测结果恢复，不是 22：

sudo systemctl stop fwknop-server
sudo iptables -D INPUT -j FWKNOP_INPUT
ss -tlnp | grep sshd          # 看看真实端口
sudo ufw limit 那个端口/tcp

或者直接让脚本还原（它会自己探测端口）：

sudo bash 10-server.sh --uninstall     # 还原 fwknopd.conf，恢复公网 SSH 规则
sudo bash 10-server.sh --purge         # 上面这些，再删掉 access.conf 与密钥包

服务端参数

参数作用
--keys FILE密钥包路径，默认 ./spa-keys.env
--close-ssh删掉公网 SSH 规则。确认客户端能进门之后再加
--status只看状态，不改任何东西
--uninstall停服务、还原 fwknopd.conf、恢复公网 SSH 规则
--purge上面这些，再删掉 access.conf 和密钥包

共用函数

三个脚本共用 lib.sh（log/warn/die、need_root、load_env、spa_keys_for、valid_name、host_count、gen_key）。改密钥包格式只需要动 spa_keys_for 一个函数。
