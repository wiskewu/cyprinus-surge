服务端 fwknopd 起不来fwknopd -F 前台跑。常见是 access.conf 里混进空格或中文标点
日志里没有 SPA 记录包根本没到。先查云安全组有没有放行 62201/udp，再 tcpdump -i any udp port 62201；两处都正常才是服务商封了 UDP

Connection closed by UNKNOWN port 65535先查 ProxyCommand 自己能不能跑。ssh 会把这一行改写成 exec <命令>，所以写成 fwknop …; sleep 2; nc … 时，exec 之后的命令根本不执行，握手前就 EOF。必须先包一层 /bin/sh -c '…'（ssh -v 里能看到实际执行的命令）。排除这条之后再看：敲门到了没（journalctl -u fwknop-server / iptables -S FWKNOP_INPUT）、端口对不对（ssh -v 里的 Port）、是不是被 fail2ban / PerSourcePenalties 封了

本机 TUN 捕获 SSH 与测速

本机跑着 Clash / sing-box 的 TUN 时，连服务器的流量也会被隧道接管（服务器 IP 不在直连规则里）。症状是 kex_exchange_identification、Connection closed by UNKNOWN port 65535，或超时，但服务器明明在跑。

先看一个假象：nc -vz 说「能通」也不可信。TUN 在本地就把 TCP 握手接住了，包括本来没任何服务监听的端口——比如 nc -vz <IP> 62201（SPA 是 UDP，服务器上根本没有 TCP 62201）也会报 succeeded。判断方法一：route -n get <服务器IP> | grep interface，输出 utunX 就是被接管了。方法二（能真正绕开 TUN 的连通性测试，macOS 上是 IP_BOUND_IF）：curl --interface en0 -sS telnet://<服务器IP>:<端口>——打到真 sshd 会出 SSH-2.0-…；用 nc -s <本机en0地址> 不行，那只是绑源地址，路由仍旧走 tun。

通用解法是配置层面的，不是去改本机路由：把服务器自己的地址设为直连——所有客户端都有这个规则，只是命令行配置不像 GUI 那样自动帮你加。

注意层级：规则必须加在「真正持有 utun 的那个客户端」里。先确认是谁：pgrep -fl 'clash|mihomo|sing-box|surge|stash' + route -n get <服务器IP> | grep interface。常见误区：机场客户端只把它自己的节点加入直连（否则环路），你自建的 VPS 不在名单里，照样被送进隧道。改 sing-box 的配置文件对 Clash Verge 的隧道毫无影响。
# sing-box：route.rules 的第一条（本手册的 50-render-client.sh 已经自动写进去了）
{ "ip_cidr": ["<服务器IP>/32"], "action": "route", "outbound": "direct" }

# Clash / Mihomo：加在 rules 里（no-resolve 防止为了匹配规则去解析域名）
- IP-CIDR,<服务器IP>/32,DIRECT,no-resolve

Clash Verge 里别改订阅自带的那份 profile（一更新就没了），用它的「全局扩展配置 → 规则」模板（prepend:）：

prepend:
  - IP-CIDR,<服务器IP>/32,DIRECT,no-resolve

不加这条的后果不只是 SSH：敲门包也会被送进隧道，到服务端时源 IP 变成隧道出口，ALLOW_IP source 就对不上号了；而 TUN 又会把那个「本地假通」回给你，看起来像 SPA 失效。

临时手段（不改代理配置时）：把那个 IP 的流量改回真实网关，或干脆关掉 TUN。

# macOS
sudo route -n add -host <服务器IP> <局域网网关>
# Linux
sudo ip route add <服务器IP> via <局域网网关>
# 用完删掉
sudo route -n delete -host <服务器IP>
本机有 TUN 时，测出来的每个数字都可能是假的。跑着代理客户端的机器会把 nc / mtr / curl 也送进隧道。验收前先确认测试机器上没有代理客户端在跑。唯一仍可靠的是 ping——ICMP 通常不被代理接管。
隧道与系统代理是两件事。停掉 TUN 客户端后仍然没网、或浏览器报错而终端正常，排查步骤与验收清单见 问题记录 1 · 隧道与系统代理残留。

与 ufw 的关系

IPT_INPUT_ACCESS   ACCEPT, filter, INPUT, 1, FWKNOP_INPUT, 1;
#                                        ↑ 第 1 位，先于 ufw 的链求值

SPA 开的口子不会被 ufw 挡掉。代价是 ufw status 里看不到这些临时规则。

ufw enable / reload / reset 会重建 INPUT 链，冲掉跳转规则，之后 SPA 静默失效（客户端不报错，SSH 直接超时）。任何 ufw 变更之后：
sudo systemctl restart fwknop-server
脚本每次改完 ufw 都会自动重启一次。

检查跳转还在不在：iptables -S INPUT | grep FWKNOP_INPUT，有输出就是正常。

嗅探端口

服务端默认只嗅探 udp port 62201。客户端用了 --rand-port 就打不进来，得把 fwknopd.conf 里 PCAP_FILTER 放宽成 udp dst portrange 10000-65535。更省事是别用随机端口。

并行接入通道

sudo ufw allow in on tailscale0

它的作用不是「SPA 坏了的备份」，而是一条独立存在的路：公网配置写错了，你仍能从 tailnet 进去修。VPS 上的 Tailscale 本身也吃 SSH 规则，两件事配套。

第二层防火墙

ufw 只是里层，云厂商安全组是外层，脚本碰不到。不在外层放行 62201/udp，敲门包到不了网卡。

已知限制

  • 不是万能。挡的是「没密钥的人连不上 sshd」。OpenSSH 自身的 0day 仍要靠及时打补丁；拿到密钥的中间人依然成立。改变的是暴露窗口。
  • 密钥就是命门。泄露 = 22 随时对攻击者开放，且日志里没有任何异常——在他看来就是一次合法敲门。
  • 需要 UDP 出境。部分校园网/公司网封 UDP 时 SPA 反而挡了你的路。
  • 服务商可能封 UDP 或非标端口。表现和「客户端丢包」一模一样，先 tcpdump 确认包到没到。
  • 脚本按 Debian/Ubuntu 写（apt + ufw + systemd；服务端包 fwknop-server、客户端包 fwknop-client）。客户端脚本已支持 brew / pacman。
